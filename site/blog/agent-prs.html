227 agent PRs in 8 weeks: 96% approved, 46% needed a fix within a week

Bohdan Kostko · November 2026

A five-person team I work with moved most of their work to Claude Code this autumn. After 8 weeks I pulled every PR they'd opened from GitHub - 227 of them - because review started to feel off and I wanted to see if it's just me

It's not just me haha

PRs got way more and way bigger

  • 4 PRs a week went to 42. Same five people
  • Median PR is 492 lines across 12 files
  • 37% are over 1,000 lines

Nobody on that team writes 1,000 line PRs by hand. The agent does, in one go, and the diff looks tidy

Review stopped blocking anything

  • 96% got approved. Only 8 of 227 ever got "changes requested"
  • One person gave 48% of all reviews

That last one is the part that worries me most. When PRs go 10x, review lands on whoever is the most conscientious, and that person becomes the bottleneck and the single point of failure at the same time

People still leave comments btw - 2,450 line comments in total. Tests 29%, error handling 18%, migrations 10%, security 8%, changed defaults 8%. So they do catch things, just in the parts they actually read

And then the fixes

  • 46% of merged PRs had a follow-up PR touching the same source files within 7 days
  • For PRs over 1,000 lines it's 65%. Under 300 lines - 30%
Under 300 lines30%

To be very fair, that's a loose proxy. It includes normal iteration ("now add the next field"), not only bugs. But the gap between big and small PRs is the part I trust, and it's big

The story behind it is the same almost every time. Clean looking agent diff, green tests, and somewhere inside it quietly changes a default, swallows an error or touches a shared helper. Someone skims it, approves it, and a week later there's a fix

What I'd try

None of it needs a tool:

  1. Cap PR size in the task, not in review. Ask the agent for the smallest PR that does X and to stop around 300 lines. Under 300 lines the fix rate was less than half
  2. Make the agent list what it changed outside of the task - defaults, error handling, public functions, files nobody asked it to touch. Read that list first
  3. Spread review on purpose. If one person does half of the reviews, that's a problem no matter how good that person is
  4. Read the risky 10% properly and skim the rest, and be honest about which is which. Migrations, auth, money and config deserve the full read

Why I'm writing this

I'm building Cockpit - a free, open source desktop app for running a bunch of Claude Code sessions at once. It came out of exactly this: more sessions, more PRs, less attention per decision. Everything that needs you lands in one queue, and PR review starts with the riskiest finding

It also has a PR report that gives you these same numbers for your own repo. It runs gh on your machine, no Claude usage, and names are left out when you copy it

Would be really curious if your team looks the same. Or if you found something that actually works - keen to hear
